## C. 圖片檔名規範（未來新增素材沿用）

1. **格式**：`{主題}-{畫面內容}.{副檔名}`，主題用產品或領域的英文短名，畫面內容描述照片實際拍到的東西。
   例：`sut-cqb-close-quarters-training`、`police-box-portable-case-exterior`、`vr-fire-scenario-residential-kitchen`。
2. **字元**：只用英文小寫、數字與 `-`。不要空白、底線、中文或日文。
3. **不要加** `final`、`new`、`v2`、`test`、`copy`、日期流水號或 `01`、`02`；同一個產品的不同照片，用畫面內容區分（`-overview`、`-operation`、`-equipment`、`-closeup`）。只有內容真的無法區分時才加編號。
4. **主題名稱要和畫面相符**：快艇用 `speedboat-`（不寫 USV），悍馬用 `humvee-`，示意圖結尾加 `-illustration`、架構圖加 `-diagram`、概念圖加 `-concept`。不要把同一個關鍵字重複堆疊。
5. **全站唯一**：同一個檔名只代表一張圖，跨頁共用同一個檔案，不要另存 `-copy`。
6. **不分語言**：三語共用一個檔案。只有圖片本身含有需要翻譯的文字時才做語言版本，加 `-tw`／`-en`／`-jp` 結尾（目前清單沒有這種圖片）。
7. **手機專用構圖**：加 `-mobile` 結尾（目前只有 HOM-02）。
8. **副檔名**：清單寫 `.webp` 的是網站最終使用的檔名。**原始素材交 JPG／PNG 即可**，只要主檔名相同（例如 `sut-cqb-close-quarters-training.jpg`），轉檔與壓縮在第二階段處理。社群分享圖用 `.jpg`；Logo、圖示用 `.svg`。
9. **未來內容**：新聞 `{活動或主題}.webp`、案例 `{客戶類型}-{產品}-{畫面}.webp`、團隊 `{英文姓名}-portrait.webp`、沿革 `{年份}-{事件}.webp`、夥伴 `{英文名}-logo.svg`（年份是內容的一部分，不算流水號）。

## D. 圖片對應方式

### 使用者要做的事
1. **照清單改檔名**：依 `IMAGE-INVENTORY.csv` 的「SEO 建議檔名」把原始照片改名，保留原本的 `.jpg`／`.png` 副檔名。不需要自己轉 WebP，也不需要裁切或壓縮。
2. **放到同一個資料夾**：
   - 建議：在 Google Drive 建一個「BXR 網站圖片／待整合」資料夾，把改好名的原始檔放進去，再把連結給我。相機原檔通常很大，放在 Drive 可以避免 Git 儲存庫越來越肥。
   - 少量圖片也可以直接上傳到 GitHub 的 `media-src/images/`（網頁上傳單檔上限 25 MB）。
3. **告訴我三件事**（可以直接寫在 Drive 資料夾的說明）：哪些是**情境示意圖**、哪些**尚未核准公開**、哪些照片裡的人物或標示**需要遮蔽**。
4. 不必一次交齊。缺的圖片會繼續顯示現有佔位框，不會出現破圖或 404。

### 第二階段系統的處理方式
1. 腳本用**主檔名**比對清單（不看副檔名），找出每張圖的 ID、存放路徑與要填入的內容欄位；名稱對不到清單的檔案會列出來，不會被默默略過。
2. 轉成高品質 WebP（最長邊上限 2560px），放到「預計存放路徑」：`src/assets/images/{brand,home,products,solutions,technologies,…}/`。原始檔不進網站。
3. Astro 在 build 時會再輸出 AVIF／WebP 和多種尺寸，網址會保留 SEO 檔名，例如 `/_astro/sut-cqb-close-quarters-training.<hash>.webp`。
4. 我看過每張實際圖片後才寫三語 Alt，取代表中「待收到圖片後確認」的暫定文字。
5. 同一張圖只放一個檔案，由 `IMAGE-SLOT-MAP.csv` 指定它出現的所有位置。

> CMS（EmDash）注意事項：正式部署若改由 CMS 後台上傳圖片，EmDash 會用自己的儲存鍵名（storageKey）存檔，`src/lib/emdash/loader.ts` 下載時也用這個鍵名，**SEO 檔名可能不會保留**。目前預覽網站讀的是 Markdown，不受影響；要走 CMS 上傳前需要先確認。

### 九、建議的資料管理架構（只是建議，本階段不實作）
目前每個圖片欄位要在 tw／en／jp **三個檔案各填一次** `src` 和 `alt`：產品／解決方案頁的 `landing` 圖片是從各語言檔案讀取，只有卡片圖（`hero.image`／`image`）是從 tw 檔讀取。同一張圖用在 5 個位置時，就要改 15 處。建議改成：

1. **圖片登記表** `src/data/images.ts`：每張圖一筆，key 就是 SEO 主檔名，內容是 `alt: { tw, en, jp }`、`kind`（實拍／情境示意圖）、`status`（公開／未核准）。
2. **自動找檔**：用 `import.meta.glob("/src/assets/images/**/*.{jpg,png,webp}")` 依主檔名找圖片。**找不到檔案時就回傳空值，現有佔位框照常顯示**，所以不會產生 404，也不會讓 build 失敗。
3. **內容欄位只寫引用**：在 tw 內容檔的圖片欄位加 `ref: sut-cqb-close-quarters-training`，en／jp 自動沿用。`need` 保留，作為佔位框文字。現有的 `resolveSlot()`（`src/lib/slot.ts`）可以直接接上這個查詢，`MediaSlot`、`PageHero`、卡片元件都不用改版型。
4. **換圖只換檔案**：同名覆蓋即可，不用修改任何頁面。
5. 這次清單裡的 `IMAGE-SLOT-MAP.csv` 就是第一版的 `ref` 對應資料。

## 盤點時發現、需要決定的事項

1. **SUT 頁 Hero 是空的**：`sut-hero.jpg` 只接在卡片欄位（`hero.image`），`landing.heroImage` 沒有填，所以 SUT 頁首屏還是佔位框。第二階段接上同一個檔案即可。
2. **SUT 核心能力的比例不一致**：三個位置的需求文字寫「4:3」，但沒有設定 `ratio`，版面實際以 **3:2** 顯示。清單依版面寫 3:2；如果要改成 4:3，第二階段要在欄位上補 `ratio`。
3. **產品卡片不會標示「情境示意圖」**：悍馬、機槍、快艇的主圖已設為情境示意圖，頁面 Hero 會加標示，但 `CardProduct`（首頁、產品總覽、關聯產品）不會。建議第二階段讓卡片也顯示標示，或卡片改用實拍設備照。
4. **核心技術頁是寫死的佔位框**：8 個技術頁（總覽＋7 頁）Hero 的「技術應用圖片位置」寫在頁面程式裡，沒有圖片欄位。第二階段要先接上欄位，圖片才放得進去。技術圖片必須是實際已實作的應用畫面，不能用概念圖代表既有成果。
5. **預設分享圖只是 512px 方形圖示**：沒有專屬圖片的頁面，`og:image` 會退回 `icon-512.png`，但 meta 寫的是 1200×630。BRD-05 準備好後，要改 `SeoHead` 的備援邏輯。
6. **首頁手機版裁切**：手機上 Hero 高度由文字撐開、接近直式，但 16:9 的封面和影片都是 `object-position: 60%` 置中裁切，三名學員會被切掉一部分。要做手機專用構圖（HOM-02）的話，也要決定手機是否繼續播放 16:9 影片。
7. **同一頁內容相近的位置**：狙擊槍主圖與解決方式圖 1、迫擊砲主圖與解決方式圖 1、無人機的三個「低空威脅」位置、悍馬與快艇的兩個「動態平台」位置，請用不同角度或畫面，備註欄已逐一寫明。USV 的整合示意圖在同一頁出現兩次（PRD-USV-03），可以考慮其中一處改放實際畫面。
8. **舊官網候選圖**：警勤模擬 8 張、智慧城市 8 張在 `docs/SOLUTIONS-IMAGE-REQUIREMENTS.md` 有舊官網網址，但內容是否符合現行版本、授權是否可用都還沒確認，所以標「待確認」，沒有算作已具備。
9. **CIS 主視覺（06_KeyVisuals）屬「合成示意」**：產品總覽目前在使用其中一張，並已標示「合成示意」。其他 KV 只列為候選（智慧城市、數位場景技術頁），使用前要業主確認，也必須標示。
10. **NOVA、MUM-T 的子頁卡片**：兩頁是軍事模擬的子頁，首頁與解決方案總覽不顯示它們的卡片，所以只需要 Hero，不需另外準備卡片圖。
